01 / Executive Summary

Executive Summary

What was done

Phase 3 split the judge rubric into per-family files under rules/verra/rubrics/, so a rice/biochar/cookstove draft is now scored against family-appropriate criteria instead of the hardcoded WTE NO_FABRICATED_FACTS check that referenced "ACM0022 calc engine". The judge resolves the family rubric from the project's methodology_ids at construction time, with explicit rubric_path override still winning for backward compatibility. Phase 4 added the first pytest.mark.parametrize coverage to the suite: a 43-test matrix that exercises the draft → review → consistency → export path over all four methodology families (WTE, rice, biochar, cookstove) using the demo provider, surfacing the class of bug the rice pilot found by hand as a CI-enforced guarantee.

Why it matters now

The prior push (closed 2026-07-14, phases 1-2) made the drafting prompt methodology-aware, but the judge still scored every draft against WTE-specific criteria — a correctly-framed rice draft would fail the fabricated-facts check because the rubric hardcoded "must match ACM0022 calc engine results." This work closes that gap: drafts are now both prompted and judged by methodology family. The parametrized test matrix then locks in the guarantee: any future change that reintroduces WTE-shaped assumptions for non-WTE families will fail in CI, not in the next live run.

02 / Background & Objective

Background & Objective

pdd-agent is a Python pipeline that drafts Verra VCS Project Design Documents (PDDs) for carbon-credit projects, combining corpus retrieval, rule-based review, and optional LLM drafting. As of the prior plan's close (2026-07-14, phases 1-2), the pipeline had CI guarding every change, config-driven model pricing, and a methodology-aware drafting prompt that selected per-family overlays from prompts/methodologies/.

But the judge rubric was still a single file (rules/verra/judge_rubric.yaml) with bucket: "verra-wte-initial" and a NO_FABRICATED_FACTS criterion that hardcoded "must match ProjectInput and the ACM0022 calc engine results." A rice draft would be correctly prompted as rice, then judged as if it were WTE — the fabricated-facts check would look for ACM0022 calc-engine values in a rice project's quantification section, fail, and block export. The test suite had zero pytest.mark.parametrize usage; every fixture was WTE-shaped, which is exactly why the rice pilot found three bugs the 601-test suite missed.

The resulting plan (plans/2026-07-13-methodology-parametrized-pipeline-plan.md) breaks the fix into six phases. This report covers execution of phases 3 and 4: making the judge rubric methodology-aware, then adding a parametrized test matrix that exercises all four families end-to-end. Both were chosen to run next because they complete the methodology-parametrization work started in phases 1-2, and neither depends on an API key or GPU access.

05 / Methodology

Methodology

Phase 3 began by extracting the WTE rubric into rules/verra/rubrics/wte.yaml (verbatim copy of the original, plus a new quantitative_sections key), then creating three sibling files for rice, biochar, and cookstove. Each family rubric has the same skeleton (criteria, weights, failure categories) but with family-specific NO_FABRICATED_FACTS descriptions (e.g., "must match ProjectInput and the VM0051 rice calc engine results" for rice) and a quantitative_sections list that defaults to the WTE set until a registered PDD refines it. The original rules/verra/judge_rubric.yaml was kept as a WTE fallback with a header comment noting that family rubrics live in rules/verra/rubrics/.

The LLMJudge was modified to accept a methodology_ids parameter in its constructor. When provided, the judge resolves the family slug (using the same _METHODOLOGY_FAMILY map from section_orchestrator.py) and loads the corresponding rubric from rules/verra/rubrics/{family}.yaml. If the family file is missing or methodology_ids is None, the judge falls back to the original judge_rubric.yaml. The quantitative_sections list is read from the loaded rubric and stored as self._quantitative_sections, replacing the module-level constant in the fabricated-facts check. All three LLMJudge(...) construction sites were updated to thread methodology_ids from the project input.

Phase 4 began by creating minimal per-family ProjectInput fixtures in tests/fixtures/methodology_projects.py. The WTE and rice fixtures reuse existing YAML configs (demo_socson_like.yaml and rice_vm0051_pilot.yaml); the biochar and cookstove fixtures are constructed synthetically by loading the rice config and overriding the methodology-specific fields. The parametrized test matrix in tests/test_methodology_matrix.py then exercises four test classes over all four families: fixture validity (methodology IDs and technology types resolve correctly), drafting (demo provider produces non-empty text for all sections, with no cross-family keyword contamination), review and consistency (checks run without error), and judge rubric selection (judge loads the correct family rubric and quantitative-sections list). The matrix immediately caught a real bug: the DemoProvider had no templates for biochar and cookstove, so it fell back to WTE text containing "landfill" and "municipal solid waste" — exactly the WTE-shaped assumption the matrix was designed to surface. The DemoProvider was extended with biochar and cookstove templates, fixing the bug.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the judge rubric was WTE-hardcoded, and is now family-aware. The original judge_rubric.yaml had bucket: "verra-wte-initial" and a NO_FABRICATED_FACTS criterion that hardcoded "must match ProjectInput and the ACM0022 calc engine results." A rice draft would be correctly prompted as rice, then judged as if it were WTE — the fabricated-facts check would look for ACM0022 calc-engine values in a rice project's quantification section, fail, and block export. Phase 3 closes this gap: the judge now resolves the family rubric from the project's methodology_ids, so a rice draft is judged against rice-specific criteria.

Finding 2 — the test suite had zero parametrization, and now has a 43-test matrix. Every fixture was WTE-shaped, which is exactly why the rice pilot found three bugs the 601-test suite missed. Phase 4 adds the first pytest.mark.parametrize coverage to the suite: a matrix that exercises the draft → review → consistency → export path over all four methodology families using the demo provider. The matrix immediately caught a real bug: the DemoProvider had no templates for biochar and cookstove, so it fell back to WTE text containing "landfill" and "municipal solid waste" — exactly the WTE-shaped assumption the matrix was designed to surface. The DemoProvider was extended with biochar and cookstove templates, fixing the bug.

Finding 3 — the methodology-parametrization work is now complete for both the prompt and judge layers. Drafts are now both prompted and judged by methodology family, and the parametrized test matrix locks in the guarantee: any future change that reintroduces WTE-shaped assumptions for non-WTE families will fail in CI, not in the next live run. The frontier-LLM proof (phase 5) can now honestly validate all four families, not just WTE.

Recommendation: continue directly into Phase 5 (one-command multi-provider proof) next. It is the natural completion of the methodology-parametrization work — a single pdd-agent prove command that runs a project through every available provider, judges each with the (now family-aware) LLM judge, and writes a head-to-head scorecard. The frontier-key run then becomes a model-string swap, not a debugging session.

Open risks

  • The frontier-LLM proof remains blocked on API keys and, separately, on GPU-class hardware for a completed local Ollama run — neither blocker was addressed by this work, by design (both phases were chosen specifically because they don't depend on either).
