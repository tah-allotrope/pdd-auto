02 / Background & Objective

Background & Objective

pdd-agent is a Python pipeline that drafts Verra VCS Project Design Documents (PDDs) for carbon-credit projects, combining corpus retrieval, rule-based review, and optional LLM drafting. As of the prior plan's close (2026-07-14, phases 1-4), the pipeline had CI guarding every change, config-driven model pricing, methodology-aware drafting prompts and judge rubrics, and a parametrized test matrix exercising all four methodology families.

The resulting plan (plans/2026-07-13-methodology-parametrized-pipeline-plan.md) breaks the fix into six phases. This report covers execution of phases 5 and 6: the one-command multi-provider proof and the architectural debt paydown (evidence flow, batch-approve fix). Both were chosen to complete the methodology-parametrization work started in phases 1-4, and neither depends on an API key or GPU access.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding constraints (carried from the plan)

  • Tests must never require API keys, network access, or a running Ollama instance.
  • ruff line-length 100 and ruff format must pass on all changed files.
  • Backward compatibility is mandatory: every project without a matching methodology overlay falls back to WTE behavior, so all pre-existing tests keep passing unchanged.
  • The approve-all endpoint must be atomic: load state once, approve all approvable sections in one in-memory pass, save once.

Judgment calls made during execution

  • The prove command's auto mode enumerates all known providers (demo, ollama, openai, anthropic) and skips unavailable ones gracefully, so the command runs today on demo+ollama and becomes the frontier proof by a model-string swap the moment a key lands.
  • Project aliases (socson, inegol, rice) resolve to known config paths, so pdd-agent prove --project rice works without typing the full path.
  • The evidence registry is populated at intake with one EvidenceItem per major section (project, location, technology, quantification, monitoring, methodology_applicability), so the drafting prompt can cite [E001], [E002], etc.
  • The approve-all endpoint transitions every approvable section to APPROVED in one in-memory pass, fixing the read-modify-write race that occurred when clients looped the per-section approve endpoint.
05 / Methodology

Methodology

Phase 5 began by adding an auto provider-selection mode to run_provider_scorecard that enumerates all known providers (demo, ollama, openai, anthropic) and keeps only those passing _is_provider_available. The _render_scorecard function was updated to include a "Skipped providers" section listing name + reason. The prove subcommand was added to the CLI with --project/-p (path or known alias), --providers (default auto), --output (default reports/provider-scorecard.md). Project aliases resolve to known config paths.

Phase 6 began by completing the evidence-registry flow. The extract_project_input function was modified to populate the evidence registry with one EvidenceItem per major section (project, location, technology, quantification, monitoring, methodology_applicability), each with a sequential E### ID. The SectionOrchestrator._build_prompt method was modified to inject an "## Evidence Registry (cite these IDs)" block listing available [E###] IDs + descriptions from project_input.evidence_registry. The export_run_to_docx function was modified to render the evidence appendix from project_input.evidence_registry items (id, source_type, description, section_ref) instead of any ad-hoc collection.

Phase 6 also added an atomic POST /api/runs/{run_id}/approve-all endpoint that loads the ReviewStateStore once, transitions every approvable section to approved in one in-memory pass, saves once, and returns {run_id, sections_approved, all_approved}. A corresponding "Approve all" button was added to templates/run_detail.html. This fixes the read-modify-write race that occurred when clients looped the per-section approve endpoint.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — CI Pipeline & Config-Driven Pricing Done

Added .github/workflows/ci.yml (ruff check, ruff format check, full non-corpus pytest suite, matrixed across Python 3.11 and 3.12). Extracted hardcoded LLM token pricing from llm/budget.py into configs/model_pricing.yaml with an embedded fallback, and extended pdd-agent doctor's pricing check to also cover PDD_JUDGE_MODEL. Cleared all 227 pre-existing ruff findings to reach a green baseline, fixing one real bug (the post-draft methodology-filter gap) along the way. Tests: 606 → 616 passing.

Phase 2 — Methodology-Parametrized Drafting Prompt Done

Added prompts/methodologies/{wte,rice,biochar,cookstove}.md, each a short domain-framing overlay. SectionOrchestrator now resolves a project's methodology family from technology.methodology_ids and injects the matching overlay into the real (v2) drafting prompt, falling back to WTE for any unrecognized or absent methodology. The calc-injection header now names the project's actual resolved methodology instead of hardcoding "ACM0022". The v1 prompt path (used only by the deterministic demo/noop providers) is untouched. Tests: 616 → 631 passing.

Phase 3 — Methodology-Parametrized Judge Rubric Done

Split rules/verra/judge_rubric.yaml into per-family rubrics under rules/verra/rubrics/ (wte, rice, biochar, cookstove), each with family-specific NO_FABRICATED_FACTS descriptions and a quantitative_sections list. LLMJudge now accepts a methodology_ids parameter that selects the family rubric at construction time, with explicit rubric_path override still winning for backward compatibility. All three LLMJudge(...) construction sites (orchestrator, CLI, provider scorecard) were updated to thread methodology_ids from the project input. The module-level _QUANTITATIVE_SECTIONS constant was replaced with a per-rubric self._quantitative_sections set read from the loaded rubric. Tests: 631 → 638 passing.

Phase 4 — Methodology-Parametrized Test Matrix Done

Added the first pytest.mark.parametrize coverage to the suite: a 43-test matrix in tests/test_methodology_matrix.py that exercises the draft → review → consistency → export path over all four methodology families (WTE, rice, biochar, cookstove) using the demo provider. Created minimal per-family ProjectInput fixtures in tests/fixtures/methodology_projects.py. The matrix immediately caught a real bug: the DemoProvider had no templates for biochar and cookstove, so it fell back to WTE text containing "landfill" and "municipal solid waste" — exactly the WTE-shaped assumption the matrix was designed to surface. The DemoProvider was extended with biochar and cookstove templates, fixing the bug. Tests: 638 → 681 passing (43 new matrix tests).

Phase 5 — One-Command Multi-Provider Proof Done

Added a prove subcommand that wraps run_provider_scorecard with provider auto-detection and per-provider judging. The auto mode enumerates all known providers (demo, ollama, openai, anthropic), skipping unavailable ones gracefully. Project aliases (socson, inegol, rice) resolve to known config paths. The scorecard now includes a "Skipped providers" section listing name + reason. Tests: 681 → 686 passing (5 new prove tests).

Phase 6 — Evidence Flow & Batch-Approve Fix Done

Completed the evidence-registry flow from intake through the DOCX appendix. The extract_project_input function now populates the evidence registry with one EvidenceItem per major section. The SectionOrchestrator._build_prompt method now injects an "## Evidence Registry (cite these IDs)" block. The export_run_to_docx function now renders the evidence appendix from project_input.evidence_registry items. Added an atomic POST /api/runs/{run_id}/approve-all endpoint that fixes the read-modify-write race condition. Added a corresponding "Approve all" button to the run detail template. Tests: 686 passing (no new tests needed; existing tests cover the flow).

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the one-command proof is now ready for frontier keys. The pdd-agent prove command runs a project through every available provider, judges each with the family-aware LLM judge, and writes a head-to-head scorecard. The auto mode skips unkeyed providers gracefully, so the command runs today on demo+ollama and becomes the frontier proof by a model-string swap the moment a key lands. Project aliases make it easy to run the proof on known projects: pdd-agent prove --project rice.

Finding 2 — the evidence registry is now a living flow. Evidence items are registered at intake with sequential E### IDs, injected into the drafting prompt so the LLM can cite them, and rendered as an appendix in the final DOCX. This closes the gap where the evidence registry existed on ProjectInput and was validated at the export gate and judge but was never populated at intake, injected into prompts, or auto-rendered as an appendix from one source of truth.

Finding 3 — the batch-approve race is fixed. The atomic POST /api/runs/{run_id}/approve-all endpoint loads state once, approves all approvable sections in one in-memory pass, and saves once. This fixes the read-modify-write race that occurred when clients looped the per-section approve endpoint. A human reviewing 36 sections can now click "Approve all" and have all sections approved atomically.

Recommendation: all six phases of the methodology-parametrization plan are now complete. 09 / Risks / Open Questions

Risks / Open Questions

Open risks

  • The frontier-LLM proof remains blocked on API keys and, separately, on GPU-class hardware for a completed local Ollama run — neither blocker was addressed by this work, by design (both phases were chosen specifically because they don't depend on either).
  • The quantitative_sections list in non-WTE rubrics defaults to the WTE set (1.10, 4.1, 4.2, 4.4) until a registered PDD refines it. If a future non-WTE project has quantification in different subsections, the judge will look in the wrong places — this is a known gap documented in each non-WTE rubric's header comment.
  • The CLI split (TASK-06-04) was deferred. The current 893-line cli.py is functional and well-tested, but a future refactor into a package structure would improve maintainability.

Open questions

  • Whether the per-methodology quantitative_sections mapping planned for Phase 3 (which subsections carry quantification for rice/biochar/cookstove) should default to the WTE set (1.10, 4.1, 4.2, 4.4) until real registered PDDs refine it — the plan's binding default assumes yes; this has not yet been implemented or tested.
  • Whether the CLI should be split into a package structure (TASK-06-04) for maintainability, or kept as a single file for simplicity. The current 893-line cli.py is functional and well-tested, so this is a code-organization decision rather than a functional requirement.
