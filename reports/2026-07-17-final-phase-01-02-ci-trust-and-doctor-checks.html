02 / Background & Objective

Background & Objective

pdd-auto is a Python pipeline that drafts Verra VCS Project Design Documents for carbon-credit projects (waste-to-energy plus three additional methodology families: rice, biochar, cookstoves). A 2026-07-16 codebase brainstorm found that GitHub Actions CI had been failing on every run since its creation three days earlier — a missing python-multipart dependency broke test collection on any fresh install, while the developer's already-provisioned local environment masked the problem entirely. Fixing that single dependency then exposed 11 further Linux-only test failures the Windows-only development history had never surfaced. Both issues were fixed in that same session, producing the project's first-ever green CI run.

The six-phase plan that followed this brainstorm has one connecting thread across its first half: make the trust infrastructure itself trustworthy — visible, enforced, and self-diagnosing — before building anything on top of it (a hardened proof harness in Phases 3–4, and a keyless frontier drafting provider in Phase 5). This report covers the two phases that deliver that foundation: PHASE-01 and PHASE-02.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions carried from the plan

  • Branch protection is applied with enforce_admins: false so the current solo direct-push-to-main workflow is not broken — the goal is visibility, not blocking the sole maintainer.
  • The repository (tah-allotrope/pdd-auto, public) supports branch protection on GitHub's free plan, confirmed via gh repo view.
  • The python-multipart package's import name varies by version, so the doctor check tries both python_multipart and multipart.

Constraints honored

  • Tests must never require API keys, network access, or a running external tool (Ollama, gws, uv) — every new test in this scope mocks subprocess.run, shutil.which, and importlib.import_module as needed.
  • ruff check and ruff format --check must pass on all new/modified files (line length 100) — verified before every commit.
  • Per the session's explicit instructions, git push origin main is deferred to a single push after both phases are committed, rather than pushed per phase.
05 / Methodology

Methodology

Each phase followed the same four-step discipline specified by the plan: implement the file changes exactly as described, run the project's full test suite plus lint/format checks and fix anything red before proceeding, stage and commit with a message describing the change and its rationale, then move to the next phase. No phase was marked complete without a locally green test run — "would a fresh install pass this?" was the standing bar, since that is precisely the question the original CI outage answered wrong for three days.

Branch protection (an API-level change, not a file change) was applied using GitHub's REST API with three required status-check contexts matching the CI workflow's rendered job names — two already confirmed from a prior live CI run (test (3.11), test (3.12)) and one predictable from the new job's YAML identifier (lock-reproducibility, which carries no matrix and therefore renders as its bare job id).

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

PHASE-01 — CI Trust Layer Done

Goal: make a red CI impossible to miss and a stale lockfile impossible to commit unnoticed.

  • Added a CI status badge as the first line under the README's H1, linking to the Actions workflow.
  • Added a second CI job, lock-reproducibility, that runs uv lock --check then a locked uv sync --all-extras install and the full test suite — so a stale lockfile (exactly what shipped for three days this week) now fails CI on its own, independent of the existing pip-based job.
  • Applied GitHub branch protection to main requiring all three check contexts (test (3.11), test (3.12), lock-reproducibility) in non-strict mode with admins exempt — confirmed live via the GitHub API, which echoed back all three contexts.
  • Truth-synced README: replaced the two-pushes-stale "544 tests pass" claim with the current collected/run/deselected counts; removed two Known Gaps bullets describing the Ollama provider and LLM judge as "stubs" (both were fixed in earlier pushes and no longer described the code); added the missing pdd-agent prove row to the CLI Commands table.

Verified: uv lock --check passed locally before the new CI job was wired in (RISK-01-01 mitigation); ruff check/ruff format --check clean; full suite 679 passed / 0 failed; grep -c "544 tests" README.md returns 0; branch protection confirmed via gh api .../protection echoing the three contexts.

PHASE-02 — Doctor Environment-Integrity Checks Done

Goal: teach pdd-agent doctor to diagnose the three environment failures that caused or masked this week's CI outage.

  • check_test_deps() — verifies pytest, python_multipart (with a fallback to the multipart import name across package versions), uvicorn, and jinja2 import cleanly; this is precisely the dependency class that broke fresh-install CI collection.
  • check_pythonpath() — warns when the PYTHONPATH environment variable is set, since a foreign PYTHONPATH injected by other tooling on the development machine was directly observed this week to shadow the project's own virtual environment.
  • check_uv_lock() — runs uv lock --check (skipping gracefully if uv isn't on PATH or uv.lock doesn't exist) so a stale lockfile is caught locally, not only by CI.
  • All three checks follow the doctor's existing contract exactly: they can only ever report OK or WARN, never FAIL — a regression test explicitly proves run_doctor() still exits 0 when all three new checks warn simultaneously.

Verified: 10 new tests added to tests/test_doctor.py (21 total in that file), all passing; manual run of pdd-agent doctor on the development machine shows all three new lines and exits 0; full suite 689 passed / 0 failed; ruff check/ruff format --check clean.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the trust-layer gap was structural, not incidental. CI existed, ran on every push, and still failed silently for three days because nothing surfaced its status outside the Actions tab itself. Phases 1–2 close that gap on two levels at once: a badge and branch protection make CI status visible and enforced at the repository level, while the three new doctor checks give any individual developer (or a future colleague's first-ever local setup) the same diagnostic power without needing to check GitHub at all.

Finding 2 — the fixes are structurally cheap relative to the risk they close. The new CI job is 18 added lines of YAML; the three doctor checks are under 90 lines of Python with 10 new tests. Both build directly on existing patterns already in the codebase (the doctor's (status, message) tuple convention; the CI job's steps mirror the existing test job's structure) rather than introducing new architecture.

Recommendation: proceed to PHASE-03 (family-aware provider system prompts) next. It is explicitly a dependency for PHASE-04 and is self-contained and non-key-gated — it can be built and fully tested with the deterministic demo provider and mocked HTTP calls, with no external service or credential required, consistent with the pattern already followed in Phases 1–2.

08 / Implementation Path

Implementation Path

Immediate next step

Removes the last known WTE-hardcoded string from the three real LLM providers (OpenAI, Anthropic, Ollama), replacing it with a family-aware system prompt selected by the project's methodology. Following steps

PHASE-06 (the Ollama dress rehearsal) is operational and needs a machine with Ollama installed — it can run independently once PHASE-04 lands, since its measurements depend on PHASE-04's honest availability and redraft-counting logic.

09 / Risks / Open Questions

Risks / Open Questions

Known limitation of this session's execution

Per explicit session instructions, the commits from Phases 1–2 were not pushed individually — a single push covers both phases plus this report at the end of the session. This means PHASE-01's exit criterion of observing a live, push-triggered CI run for these specific commits was not performed mid-session; branch protection was instead applied using check-context names already confirmed from a prior live run (test (3.11), test (3.12)) plus one predictable name for the new job (lock-reproducibility, which has no build matrix). The first real CI run against these commits will occur when this branch is pushed — that run should be watched once, per the plan's own OBS-001 verification item.

Carried-forward risks (not yet exercised)

  • RISK-003 (from the plan): branch protection with enforce_admins: false does not physically block a red push by the repository owner — it provides visibility, not enforcement, against the sole maintainer. Accepted per the plan; revisit if the team grows.
  • PHASE-03's golden-equality bar (CON-003) requires the WTE system-prompt string to remain byte-identical after refactoring — a subtle whitespace or wrapping difference would silently break this. The plan's mitigation (write the golden test against the current literal first, then refactor) should be followed exactly.
