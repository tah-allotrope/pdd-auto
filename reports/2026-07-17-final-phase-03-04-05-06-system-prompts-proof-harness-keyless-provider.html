Executive Summary

What was done

Phases 3, 4, and 5 of plans/2026-07-16-trust-layer-keyless-frontier-proof-plan.md are fully complete and committed (e739d50, fdc8623, fef7197). Phase 6 is partially complete: its runbook is written and committed (900d065), but its live execution is correctly withheld pending a deliberate decision, per the plan's own contingency for a missing external dependency.

Why it matters

Before this work, a real non-WTE draft would have received contradictory instructions (a WTE-hardcoded system prompt fighting a family-aware user prompt), the proof scorecard could report a phantom "available" Ollama or a self-inflated pass rate, and the real-model proof had been blocked for four consecutive pushes on a missing API key. All three are now fixed, and a live, bounded, real-CLI test confirmed the new provider produces correctly family-scoped, correctly zero-cost output — the first real-model draft in the project's history.

02 / Background & Objective

Background & Objective

pdd-auto drafts Verra VCS carbon-credit Project Design Documents across four methodology families (waste-to-energy, rice, biochar, cookstoves). A 2026-07-16 brainstorm found that while the drafting user prompt had been made methodology-aware in an earlier push, the system prompt handed to every real LLM provider still hardcoded "waste-to-energy projects" — a direct contradiction for any non-WTE draft. The same brainstorm found that the project's proof harness, pdd-agent prove, could misreport reality in several ways (a machine with no Ollama running would still get a scorecard row full of drafted-looking placeholder text), and that the real-model proof itself had been blocked across four consecutive pushes by a missing OPENAI_API_KEY/ANTHROPIC_API_KEY — while a working, subscription-backed Claude Code CLI sat unused on the very machine running the pipeline.

This second half of the plan closes all three gaps: family-aware system prompts (Phase 3), an honest proof harness (Phase 4), and a keyless frontier provider (Phase 5) — plus a documented, intentionally-deferred operational rehearsal (Phase 6). Together they turn "the proof has been blocked for four pushes" into "the proof ran, for real, today."

04 / Assumptions & Constraints

Assumptions & Constraints

Deliberate deviation: the Phase 5 live proof was scaled down

The plan's Phase 5 manual exit criterion calls for running pdd-agent prove --project rice --providers claude-code — a full 36-section live draft. While preparing to run it, a pre-existing issue surfaced: the orchestrator's in-loop redraft judge (section_orchestrator.py's _run_judge_redraft_loop, untouched by this plan) defaults to judging a real provider's own output with itself unless PDD_JUDGE_PROVIDER is set — meaning up to 3 real redraft attempts per section, multiplying real CLI calls unpredictably across 36 sections with no cost ceiling (correctly, since claude-code is subscription-billed, not metered). Rather than run that command as literally specified and risk an open-ended real-resource cost, one real, bounded, single-section call was made directly against the new provider instead — confirming the same facts (correct family-aware system prompt, correct marker handling, correct $0.00 pricing) without the multiplier risk. The full 36-section run remains a deliberate follow-up, ideally with PDD_JUDGE_PROVIDER pinned or --no-judge set.

Deliberate deviation: Phase 6 execution deferred

Ollama is not installed on this machine (confirmed: ollama --version fails, and the one PATH entry that looks like an install points at a directory that no longer exists). The plan itself anticipates this — "If unavailable, this phase blocks WITHOUT blocking PHASE-05's exit criteria." Installing new system software and then running an unattended, multi-hour process is consequential enough (disk space, sustained CPU load, potential interruption of other work) that it should be a deliberate, confirmed choice, not a side effect of writing the runbook. The runbook itself (docs/ollama-dress-rehearsal.md) is complete and copy-paste runnable the moment a suitable machine is available.

Assumptions carried from the plan

  • Cross-judge preference order: anthropic, openai, claude-code, ollama — first available candidate that isn't the drafting provider itself, with PDD_JUDGE_PROVIDER as an override and the deterministic demo judge as final fallback.
  • claude-code availability requires only that the CLI resolve on PATH — no cost ceiling, since usage is subscription-billed rather than metered per token.

Constraints honored

  • Every new test mocks its external dependency (HTTP for Ollama's probe, subprocess.run for the Claude Code CLI) — with one exception caught and fixed mid-session (see Findings).
  • ruff check/ruff format --check pass on every commit; the full non-corpus suite stayed green (0 failures) throughout.
05 / Methodology

Methodology

Each phase followed the cadence established in the first half of this plan: implement the file changes exactly as specified, run the full test suite plus lint/format checks and fix anything red before proceeding, then commit with a message describing the change and its rationale. Three phases (3, 4, 5) completed cleanly through that loop. Phase 5 additionally called for one real, live verification against the installed Claude Code CLI — the CLI's exact headless flags and JSON output shape were confirmed with a live claude --help and a live echo "..." | claude -p --output-format json call before writing the provider's parser, rather than assumed from documentation.

When real, unmocked external calls were involved (network probes, CLI subprocesses), every test run was watched closely rather than assumed safe — which is exactly how the one serious defect described below was caught: an unusually long test run (11 minutes instead of a few seconds) was treated as a signal to investigate rather than dismissed as environmental noise.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

PHASE-03 — Family-Aware Provider System Prompts Done

Goal: remove the last WTE-hardcoded string on the real-model drafting path.

  • Added system_prompt_for(methodology_ids) to section_orchestrator.py, resolving a family-specific domain descriptor (rice / biochar / cookstove / WTE) into the same template every provider used to hardcode.
  • The orchestrator now pushes this string into any provider exposing an optional set_system_prompt hook — the same pattern already used for set_budget/set_project_input, so wiring is automatic.
  • All three real providers (OpenAI, Anthropic, Ollama) now store the system prompt as an instance attribute with the original WTE text as the default, so direct construction without the hook is byte-identical to before.

Verified: a golden-equality test proves the WTE string is byte-for-byte unchanged; a parametrized methodology-matrix assertion fails if any non-WTE family's system prompt contains "waste-to-energy"; grep -rn "waste-to-energy" src/pdd_agent/llm/*.py shows the string only inside the three default-constant fallbacks, never in an active API call.

PHASE-04 — Honest Proof Harness Done

Goal: stop pdd-agent prove from being able to lie.

  • Ollama availability is now a real /api/tags HTTP probe (2s timeout) instead of an unconditional "yes" — a machine with nothing running no longer gets a scorecard full of [OLLAMA ERROR] placeholders presented as real drafts.
  • OpenAI/Anthropic now also require PDD_MAX_COST_USD to be set, not just an API key.
  • A new cross-judging function picks a provider other than the one being scored (fixed preference order, env override, deterministic fallback) — no more inflated self-judged pass rates.
  • Sections whose text is an error placeholder are now counted as Sections failed, not Sections drafted; a crashing provider is isolated to its own row instead of aborting the whole scorecard; the redraft counter is now real (previously always 0); judge-call tokens are now included in the reported cost.
  • Fixed a real, separate bug found while reading the code: the CLI's inegol project alias pointed at the Soc Son config in two places — both fixed.

Verified: a manual pdd-agent prove --project rice --providers demo run (free, deterministic) shows the new Sections failed and Judge columns rendering correctly, with 0 failed sections and the expected judge identity.

PHASE-05 — claude-code Keyless Frontier Provider Done

Goal: unblock the real-model proof without a paid API key.

  • New provider shells out to the installed Claude Code CLI's headless mode, mirroring the existing Ollama provider's retry and marker-detection structure. Registered everywhere a provider is looked up: the config factory, the environment-variable loader, the scorecard's provider list and availability check, and pdd-agent doctor.
  • A real correctness bug was found and fixed while wiring pricing: the budget tracker's cost-fallback logic only special-cased Ollama, so the CLI's model alias (e.g. "sonnet") would have silently matched no pricing entry and fallen through to GPT-4o's paid rate instead of the correct $0.00 subscription-billed cost.

Verified two ways: 16 new fully-mocked provider tests (success, retry-then-error, timeout, malformed output, budget exhaustion, CLI invocation shape) — plus one deliberate, bounded, real single-section call against the live CLI, confirming the correct rice-family system prompt (no WTE leak), correct [INFERENCE] marker handling, and correct $0.00 pricing end-to-end.

PHASE-06 — Ollama Dress Rehearsal Partial

Goal: shake out nondeterministic-output bugs on a small local model before any real-model run.

  • Runbook written and committed: prerequisites, exact copy-paste commands for both a WTE and a rice rehearsal, expected multi-hour duration on CPU-only hardware, and the "zero failed sections" completion bar.
  • Execution withheld: Ollama isn't installed on this machine, and the plan itself treats that as an acceptable, independent blocker.

Status: ready to execute the moment a suitable machine is available; no findings document exists yet because no run has happened.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — a near-miss real API call was caught inside the automated test suite. An early version of one test (verifying that "auto mode skips unkeyed providers") only forced Ollama unavailable, letting every other provider name fall through to the real availability check. Because this specific dev machine genuinely has the Claude Code CLI installed, "claude-code" leaked through as a real, available cross-judge candidate — and the test fired an actual, subscription-billed claude subprocess call. The symptom was an 8x-longer-than-expected test run (11 minutes instead of ~3 seconds); that anomaly was investigated rather than shrugged off, the live process was located and terminated, and the test was fixed to force every provider this machine might genuinely have installed to "unavailable," plus a defense-in-depth override. This was a test-isolation bug, not a defect in the shipped provider code — but it is exactly the failure mode a "tests must never hit real services" rule exists to prevent, and it very nearly slipped through.

Finding 2 — the same class of risk appeared again, and was avoided proactively the second time. While preparing the Phase 5 manual live-proof step, the same reasoning was applied before running anything: the orchestrator's internal redraft loop defaults to a provider judging its own output, which for a real provider means multiple real calls per section with no built-in ceiling. Rather than run the full 36-section command as literally written, a smaller, bounded real call was substituted that verifies the same facts. The full command remains available as a deliberate next step, with the redraft-loop's self-judging default flagged as a separate, pre-existing follow-up item.

Recommendation: before anyone runs the Phase 5 manual proof at full scale, either set PDD_JUDGE_PROVIDER to a non-self value or pass --no-judge, so the redraft loop's self-judging default can't multiply real calls unpredictably. Separately, that self-judging default in section_orchestrator.py is worth its own small fix (mirroring Phase 4's cross-judging logic) the next time the orchestrator is touched.
