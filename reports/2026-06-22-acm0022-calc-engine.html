The engine is pure Python with Pydantic I/O — no LLM involved — satisfying CON-001 (VVBs require reproducible calculations).

3. Math / Algorithm Used

The engine implements the full ACM0022 v3.0 equation set with five CDM Tool integrations. The core algorithm is the First Order Decay (FOD) model from CDM Tool 04, which calculates time-dependent methane generation from waste disposed in a solid waste disposal site.

CDM Tool 04, Equation 2 — FOD Model (Baseline Methane)
BECH4,y = φ × (1 − fy) × GWPCH4 × (1 − OX) × (16/12) × F × DOCf × MCF × Σx=1..y [Wj,x × DOCj × e−kj(y−x) × (1 − e−kj)]
CDM Tool 05, Equation 2 — Baseline Electricity Displacement
BEEC,y = Eexported × EFgrid × (1 + TDL)
CDM Tool 03, Equation 1 — Fossil Fuel Emissions
PEFC,y = FCi × NCVi × EFCO2,i
CDM Tool 14, Equation 4 — AD Methane Leakage
PECH4,y = QCH4 × EFCH4,default × GWPCH4
CDM Tool 06, Equation 15 — Incomplete Flaring
PEflare,y = GWPCH4 × FCH4,RG × (1 − ηflare)
ACM0022, Equation 36 — Net Emission Reductions
ERy = BEy − PEy − LEy

6. Limitations / Second-Best Alternative

  • Single-year calculation: The engine calculates one year at a time (specified by calculation_year). For a full crediting period time series, the caller must loop and sum. This is by design — the FOD model's year parameter is the crediting period year, not a calendar year.
  • Constant annual waste input: The FOD model assumes constant annual waste input (Wj,x = Wj for all x). The published Inegol PDD uses year-by-year varying waste inputs, which explains why a single-year calculation won't exactly match the published year-by-year table. A future enhancement could accept a waste input schedule.
  • CDM Tool 07/12 not implemented: The plan listed Tool 07 (fossil fuel displacement) and Tool 12 (baseline identification), but the actual Inegol PDD uses Tools 03, 04, 05, 06, and 14. The implemented tool set matches what's actually used in ACM0022 WTE projects.
  • Grid EF is user-provided: Tool 05 does not calculate the combined margin EF (which requires OM and BM decomposition). The user provides the EF directly, as is standard practice for WTE PDDs in the Verra ecosystem.

Second-best alternative: A spreadsheet-based calculation (as commonly used in the industry) would provide the same mathematical results but without Pydantic type safety, programmatic auditability, or integration with the pipeline's review and export layers.

8. Open Questions / Next Phase Seeds

Phase 2 Prerequisites

  • LLM provider: Phase 2 wires OpenAI GPT-4 into the pipeline. The calc engine provides the emission numbers; the LLM drafts the prose that cites them. The bridge is QuantificationInputs.from_calc_result().
  • Prompt injection: Calc results should be injected into the drafting prompt as structured data (not free text) to prevent the LLM from hallucinating different numbers.
  • Year-by-year table: VCS PDDs require a crediting-period emissions table. The caller should loop calculation_year=1..N and format the results. This is a presentation concern for Phase 2, not a calc engine concern.

Deferred Enhancements

  • Variable annual waste input schedule (vs constant Wj)
  • Multiple crediting period scenarios (optimistic/conservative)
  • Uncertainty analysis (Monte Carlo on key parameters)
  • Country-specific default parameter lookup (IGES database integration)
