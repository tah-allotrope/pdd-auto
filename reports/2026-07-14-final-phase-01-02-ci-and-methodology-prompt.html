01 / Executive Summary

Executive Summary

What was done

Phase 1 added a GitHub Actions CI workflow (lint + format + full test suite on Python 3.11 and 3.12) and moved hardcoded LLM pricing into a YAML config the environment doctor now validates. Getting there required clearing 227 pre-existing lint findings across the codebase — one of which turned out to be a real, previously undetected bug, not dead code. Phase 2 then split the drafting prompt's waste-to-energy framing out into methodology-specific overlay files, selected automatically from each project's declared methodology, so a rice, biochar, or cookstove project is finally prompted as what it actually is.

Why it matters now

The prior push (closed 2026-07-12) made the pipeline's code paths real — a working Ollama provider, a real LLM judge, a live registry downloader — but never noticed that the prompt text the model actually reads was still hardcoded to one methodology family. The moment a frontier API key lands, the very first real draft of a non-WTE project would have been silently mis-prompted. This work closes that gap before it becomes an expensive mistake.

02 / Background & Objective

Background & Objective

pdd-agent is a Python pipeline that drafts Verra VCS Project Design Documents (PDDs) for carbon-credit projects, combining corpus retrieval, rule-based review, and optional LLM drafting. As of the prior plan's close, the pipeline supported four methodology families end-to-end at the calculation-engine level: waste-to-energy (ACM0022), rice cultivation (VM0051), biochar (VM0044), and improved cookstoves (AMS-II.G).

A July-13 codebase analysis (research/2026-07-13-pdd-post-reality-gap-next-level-brainstorm.md) surfaced a sharper finding than any prior review: the calc engines and the ProjectInput schema were genuinely multi-family, but the two artifacts the LLM actually reads to draft a section — the drafting prompt and the judge rubric — were still hardcoded to describe every project as waste-to-energy. The one existing non-WTE pilot (a synthetic rice project) only avoided this because it used a deterministic demo provider that never sees the real prompt text.

The resulting plan (plans/2026-07-13-methodology-parametrized-pipeline-plan.md) breaks the fix into six phases. This report covers execution of the first two: establishing CI as a safety net, then making the drafting prompt methodology-aware. Both were chosen to run first specifically because neither depends on an API key or GPU access — they are ready today, independent of the external blockers (no OpenAI/Anthropic keys, no GPU) that have stalled the frontier-LLM proof for three consecutive pushes.

  • ruff line-length 100 and ruff format must pass on all changed files.
  • Backward compatibility is mandatory: every project without a matching methodology overlay falls back to WTE behavior, so all pre-existing tests keep passing unchanged.

Judgment calls made during execution

05 / Methodology

Methodology

Each phase followed the same discipline: implement the plan's file changes, run the full test suite, fix any failure before committing, then commit. Phase 1's target of a clean ruff check . turned out to be non-trivial — the repository had 227 pre-existing lint findings, none related to this work. Rather than silently disabling checks to reach green, each finding was triaged individually: safe mechanical fixes (unused imports, f-strings without placeholders) were auto-fixed; a genuinely undefined forward-reference type hint was fixed with a proper TYPE_CHECKING guard; a pervasive, intentional sys.path/load_dotenv-before-import pattern was allow-listed at the project level rather than risking reordering that could break runtime behavior; and every one of the 17 unused-variable findings was individually inspected rather than blanket-deleted.

That inspection surfaced one real bug: MethodologyRules.run_post_draft_checks() computed a per-check applies_to methodology filter but never applied it, so an ACM0022-only compliance check (the Section 1.16 REC/electricity check) was firing unconditionally for every project, including the rice pilot. This was fixed at the root — threading methodology_ids through from its sole call site — with a dedicated regression test, rather than deleting the unused variable and leaving the filtering gap in place.

Phase 2 began by locating where the drafting prompt's WTE-specific text actually lives. prompts/section_draft_v2.md turned out to be documentation of the prompt, not a template loaded at runtime — the real prompt is assembled in Python inside SectionOrchestrator._build_prompt(). The fix therefore had two parts: bring the documentation file's language in line with reality (methodology-neutral), and build the actual runtime mechanism — a methodology-to-family resolver and four overlay files loaded and injected into the assembled prompt. A first draft of the non-WTE overlays told the model "do not use waste-to-energy framing (landfill, biogas combustion, municipal solid waste...)" — a new test asserting the absence of those exact words caught that the negative instruction was itself injecting the poison words into the prompt. The overlays were rewritten to describe each project positively instead, with no WTE vocabulary present at all.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the lint baseline was not actually clean. Setting up CI is normally mechanical, but this repository had never had a "does the linter pass" gate, so 227 findings had accumulated. One was a real, currently-live bug (see Finding 2); the rest were genuinely dead code or a deliberate, pervasive import-ordering pattern that was correctly allow-listed rather than "fixed" in a way that risked breaking working behavior.

Finding 2 — a methodology-filter bug was already live before this work started. run_post_draft_checks() silently ran an ACM0022-only compliance check against every project regardless of methodology. This predates this plan; it was found only because lint cleanup forced a close look at an "unused" variable that turned out to matter. It is now fixed and regression-tested.

Finding 3 — the drafting prompt's WTE-hardcoding was real and is now closed for the prompt layer. The overlay mechanism is generic, backward-compatible (WTE is the default for anything unrecognized), and test-verified for all four families. The judge rubric (Phase 3) has the same class of gap and remains open — a draft is now correctly framed by methodology, but not yet scored by a methodology-appropriate rubric.

Recommendation: continue directly into Phase 3 (judge rubric) next. It is the natural completion of Phase 2 — a project can now be drafted correctly by methodology but would still be judged against WTE-specific pass/fail criteria, which is an inconsistency worth closing before Phase 4's test matrix locks in behavior across all four families.

09 / Risks / Open Questions

Risks / Open Questions

Open risks

  • The frontier-LLM proof remains blocked on API keys and, separately, on GPU-class hardware for a completed local Ollama run — neither blocker was addressed by this work, by design (both phases were chosen specifically because they don't depend on either).
  • The calc-injection function's field decomposition is still ACM0022-specific; if a future phase wires the rice/biochar/cookstove calc engines into live prompt injection (they are not today), that decomposition will need a proper per-methodology rewrite, not just a header fix.
  • Four of six plan phases remain unexecuted; the methodology-parametrization work is incomplete until at least Phase 3 (judge rubric) lands, since a correctly-framed draft is currently still judged by WTE-specific pass/fail criteria.

Open questions

  • Whether the per-methodology quantitative_sections mapping planned for Phase 3 (which subsections carry quantification for rice/biochar/cookstove) should default to the WTE set (1.10, 4.1, 4.2, 4.4) until real registered PDDs refine it — the plan's binding default assumes yes; this has not yet been implemented or tested.
  • Whether the logged service batch-approve-all defect (Phase 6) reproduces reliably enough to write a deterministic regression test, or requires deeper investigation of the review-state-store's concurrency behavior first.
