01 / Executive Summary

Executive Summary

What this closes

Three months of prior work had produced a mature-looking pipeline whose intelligence layer was never actually exercised — every demo used deterministic placeholder providers, the review service silently forced demo mode and disabled its own retrieval, and the methodology-breadth claim (four Verra families) had never been drafted end to end. This push made all of that real, or documented precisely why a piece of it can't be made real yet (missing API keys, this machine's CPU-only hardware).

What shipped

  • A working local-LLM provider (Ollama), live-verified against a real running instance.
  • A FastAPI review service with no more import-time monkeypatching, thread-safe retrieval, and a real provider opt-in/fallback system with a visible dashboard banner.
  • An LLM-judge that parses structured JSON findings instead of scraping a bare number, with cost-tiered model selection.
  • A real (if currently fallback-mode) Verra registry downloader and three new corpus configs.
  • A complete non-WTE (rice cultivation) project drafted, reviewed, and exported through both the CLI and a live service instance — proving the pipeline isn't secretly WTE-only.
02 / Background & Objective

Background & Objective

pdd-agent drafts Verra VCS Project Design Documents for carbon-credit projects using corpus retrieval, rule-based review, and a DOCX export pipeline. A prior push (closed 2026-07-05) added the skeleton for real-LLM drafting — an Anthropic provider, a judge/redraft loop, a FastAPI section-review service, and calc engines for three additional methodology families beyond the original waste-to-energy (WTE) focus. But a research brief written the following week (research/2026-07-12-pdd-post-convergence-brainstorm.md) found that none of it had actually been proven: every artifact ever produced used deterministic demo/noop providers, the service hard-forced demo mode and disabled corpus retrieval to avoid a threading bug, and none of the three new methodology families had ever been drafted.

The resulting plan (plans/2026-07-12-pdd-reality-gap-plan.md) set a single objective: close the reality gap — exercise the real-LLM drafting path, make the service use its own real retrieval and providers, and prove the methodology breadth by actually drafting a non-WTE project — across six phases, three of them explicitly designed to complete without any API key.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding constraints (plan-defined)

  • Tests must never require API keys, network access, or a running Ollama instance — every test mocks its HTTP.
  • Demo/noop providers stay the default everywhere; real providers are opt-in via environment variables only.
  • Local-only deployment — no cloud or container infrastructure this push.

Real-world constraints discovered mid-push

  • No OPENAI_API_KEY / ANTHROPIC_API_KEY in this environment — the plan anticipated this and designed Ollama as the key-independent proof path.
  • This dev machine has no GPU (Intel i5-8250U, integrated graphics only) — discovered only after installing Ollama and timing a real request. A full 36-section CPU-only draft run does not complete in a practical time window; this is a hardware fact, not a code defect, and is documented with concrete timing evidence.
  • The Verra registry's exact search API shape could not be fully reverse-engineered without browser devtools access — the implementation falls back to a documented manual-download mode, which the plan explicitly designed as an acceptable outcome.
05 / Methodology

Methodology

Each phase's exit criteria were treated as a literal, testable bar rather than a checklist to sign off from memory: code changes were followed immediately by running the affected tests, and — wherever the phase's own goal was to prove something real — by an actual live command against a running Ollama instance, a running FastAPI service, or the live Verra registry, not just a mock. That discipline is what surfaced the bugs described in Section 07: several were only visible when a genuinely non-default configuration was exercised (a redirected run directory, a non-WTE project, a real HTTP timeout), which is exactly the class of bug the reality-gap push existed to find.

Phases were sequenced by their real dependency graph (PHASE-02 and PHASE-05 are independent and were done in parallel-equivalent order; PHASE-03 built on PHASE-02's provider config; PHASE-04 built on both; PHASE-06 exercised PHASE-03's service and PHASE-05's corpus configs). Every phase closed with a full-suite regression run before moving to the next.

07 / Findings & Recommendation

Findings & Recommendation

Core finding: the pipeline's engineering was sound, but nearly every "reality" claim in the prior push was unverified. Every one of the 7 bugs found this session was a case where code looked correct on inspection and passed its existing tests, but broke the instant it met a genuinely real condition — a real HTTP timeout, a real non-default directory, a real non-WTE project, a real API key path. This is exactly the failure mode the reality-gap plan was written to hunt down, and it justifies the plan's own thesis: demo-provider test coverage alone cannot catch bugs that only manifest under real conditions.

Recommendation: treat this pattern as a standing practice, not a one-time push. Before claiming any pipeline capability is "done," exercise it against the most real condition available — even a slow, imperfect one (like CPU-only Ollama) surfaces bugs that a perfectly-passing mocked test suite cannot.

Rejected alternative: waiting for API keys before touching the real-LLM path at all. This was explicitly rejected in the plan and vindicated here — the free, local Ollama path alone surfaced 2 of the 7 real bugs found this session, independent of any external dependency.

08 / Implementation Path

Implementation Path

Immediate — when API keys arrive

Run the checklist in docs/2026-07-12-provider-scorecard-checklist.md: three-provider scorecard on the Inegol project, pick a default drafting model, get a domain expert's VVB-desk-review sign-off on the resulting DOCX. Everything except the live API call is already implemented and tested.

Near-term — better hardware for the Ollama proof

Re-run the full 36-section Ollama shakeout on GPU-equipped hardware (or a remote GPU-backed Ollama instance) to get a completed run, not just a verified-correct-under-failure one. The code path itself needs no further changes.

Near-term — finish the registry corpus

Get browser-devtools access to the Verra registry search UI to capture the real request shape, or proceed with manual PDF downloads (a bounded, one-time task per methodology family) to populate the rice/biochar/cookstove corpora and replace their synthetic golden-test numbers.

Ongoing — a real non-WTE prospect

The rice pilot is a synthetic stand-in for the externally-blocked Seraphin project. Identifying a real Vietnam rice prospect would let the schema-split decision (deferred this push per DEC-004) be made on real data instead of a synthetic proof.
