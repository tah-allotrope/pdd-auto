Background & Objective

pdd-agent is a Python pipeline that drafts Verra VCS Project Design Documents (waste-to-energy under ACM0022, plus rice/biochar/cookstove methodologies) by combining corpus retrieval, an LLM drafting layer, and a deterministic calculation engine, with a rule-based review layer gating what can export. The project has repeatedly deferred its first full-scale, real-model (non-demo, non-noop) drafting run while it closed correctness and trust gaps that would have made that run misleading if executed early: a truncating output-normalizer bug, an under-grounded retrieval index, a mis-modeled baseline methane term, an in-loop judge that could judge its own output, and calc numbers that were never carried into the exported document at all.

The objective handed to this session was to finish whatever unit of work was interrupted, then execute all three standing plans in the specified order — proof-readiness fixes, then calc correctness and audit trail, then the CI/trust layer — verifying via git history and each plan's own checkboxes rather than assuming prior status notes were current.

Findings & Recommendation

What PHASE-05 of calc-correctness actually changed

Three of the eleven Verra DOCX table renderers were dead code — implemented, tested in isolation, but with nothing in the drafting pipeline ever populating the structured_content field that triggers them. PHASE-05 wires the calc engine as the producer for two of them:

  • Section 4.4 (emissions summary) now renders a live year-by-year table straight from the calc engine's annual ER schedule, instead of staying prose-only.
  • Section 5.2 (monitoring parameters) now renders a live table from the calc engine's required-monitoring-parameters list.

Alongside that, the plan required resolving a latent ambiguity: the calc engine and the human-entered ProjectInput.quantification fields are two independently-populated sources for the same four numbers, and nothing previously declared which one wins or when a disagreement between them mattered. The fix implemented here (per the plan's own S-3 specification): a missing declaration is not a disagreement (skip it); any surviving relative delta above 5% raises a HIGH-severity consistency flag (downgraded from the previous CRITICAL, so it produces a watermarked draft export rather than a hard block); and an explicit opt-in environment variable, PDD_CALC_AUTHORITATIVE=1, lets the calc engine's numbers override the human-entered ones in drafting prompts when set.

RuleBehavior
ProjectInput field is NoneNo flag (absence isn't disagreement)
Relative delta ≤ 5%No flag
Relative delta > 5%HIGH flag, exports as watermarked DRAFT
PDD_CALC_AUTHORITATIVE unsetPrompts use ProjectInput.quantification
PDD_CALC_AUTHORITATIVE=1Prompts use calc engine scalars

Two pre-existing tests (test_no_calc_injection_in_section_1 in both test_prompt_assembly.py and test_e2e_inegol_draft.py) asserted the old, narrower injection scope (calc facts visible only in Section 4). Widening injection to Sections 1 and 4 was an explicit plan requirement (S-3 step 6), so both tests were updated to assert the new, intended behavior rather than left red or deleted.
