01 / Executive Summary

Executive Summary

What was done

Three of the six phases in the 2026-08-13 grounding-rebuild plan were implemented, tested, and merged to main: PHASE-01 (a one-command corpus-health report), PHASE-02 (rebuilding the retrieval index on real section text instead of truncated page fragments, with methodology-family filtering), and PHASE-03 (making the exported DOCX render narrative prose and its structured table together, and wiring five more of Verra's eleven table types). All three landed with the full non-corpus test suite green — 823 passed, 0 failed, up from a baseline of 798 — and ruff check / ruff format --check clean throughout.

What matters

The retrieval substrate every provenance citation and grounding metric in this system depends on was measurably broken — 73.4% of indexed text was duplicate running headers and page numbers, and one of every four corpus documents contributed nothing. That is now largely fixed for 13 of 17 documents. The remaining 4 — including the ACM0022 methodology text itself — fail for a different, upstream reason (PDF heading extraction in ingest/normalize.py), which this push root-caused but deliberately did not fix, since it falls outside PHASE-02's declared scope. The plan's real-money smoke test (PHASE-04) and everything gated behind it (PHASE-05 calc-composition fix, PHASE-06 table-aware ingestion) were explicitly deferred at the user's direction before implementation began.

02 / Background & Objective

Background & Objective

pdd-agent drafts Verra VCS Project Design Documents for waste-to-energy projects, grounding its output in a corpus of registered VCS PDDs via a "corpus-bucketed RAG" retrieval index — a name that, going into this push, no longer described the system's actual behavior. A 2026-08-13 research brief measured the index directly: 1,015 rows held only 270 distinct texts (73.4% duplication), 97.7% of rows were exactly 500 characters, and 4 of 17 normalized source documents contributed zero rows — because the indexer read a whole PDF page per heading and truncated it, so every heading sharing a page collapsed to one byte-identical, often irrelevant, string (running headers, page numbers). Separately, the exported DOCX's structured-table renderers were found to delete a section's narrative the moment a table was attached, and the ACM0022 calculation engine was silently dropping a third of a project's declared waste throughput. The resulting plan, plans/2026-08-13-grounding-rebuild-and-calc-inputs-plan.md, laid out six phases to address all of this plus a bounded real-model smoke test. This push's objective was to execute the three phases that rebuild trust in retrieval and export — the foundation the calc and real-model phases depend on — cleanly and verifiably, and to be honest about what still doesn't work rather than declaring victory early.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding assumptions carried from the plan

  • ASM-001/002: a document's text_blocks and headings are aligned by construction, one block per heading; chunks cap at 2,000 characters with 200-character overlap and an 80-character minimum.
  • ASM-003/004: any corpus document not explicitly mapped in configs/corpus_families.yaml defaults to the wte methodology family; a family-filtered search that returns nothing falls back to an unfiltered search with a loud warning, rather than failing silently.
  • DEC-003: the legacy page-fragment fallback (_find_content_page) is retained, not deleted — some documents' alignment check fails and must still degrade gracefully rather than yielding nothing.

Constraints held throughout

  • Every phase except the (deferred) real-model phase had to be fully verifiable offline — no API keys, no network calls, no Ollama dependency.
  • ruff check . and ruff format --check . are CI gates and had to pass clean at the end of every phase.
  • A stray PYTHONPATH from an unrelated local tool (a "hermes" agent venv) silently redirects Python imports to the wrong site-packages on this machine; every test invocation in this push explicitly cleared it first.
  • data/index/ and data/corpus/ are both gitignored — rebuilding the index changes no file the repository tracks, so the numbers in this report are locally measured, not committed artifacts.
05 / Methodology

Methodology

Each phase was assigned to a separate agent working in its own isolated git worktree, so PHASE-01 (retrieval diagnostics) and PHASE-03 (export rendering) — independent per the plan — could run concurrently without file collisions, while PHASE-02 (which depends on PHASE-01's code) was launched only after PHASE-01 was committed to the branch it forked from. Every phase followed red/green TDD: the plan's own test specifications were implemented first, run to confirm they failed against the old code, then made to pass with the minimum implementation the specification called for. Each phase's diff was reviewed, merged into main, re-verified against the full test suite and linter on the integrated tree (not just in isolation), and committed separately before the next dependent phase began — so a failure at any point would leave the tree at a known-good prior commit rather than a half-merged state.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

PHASE-01 — Make Corpus Health Measurable commit 8b77742

Before touching the indexer, built the instrument to prove whether later changes worked: RetrievalIndex.build() now tracks rows-per-document and surfaces any document that yields zero indexable sections as a loud warning instead of vanishing silently; a new index_health() diagnostic and pdd-agent index-report CLI command report duplication rate, truncation, and document coverage on demand. Run against the pre-rebuild index, it reproduced the research brief's numbers exactly: 1,015 rows, 270 distinct texts, 73.4% duplication, 13 of 17 documents. 16 new tests, all passing.

PHASE-03 — Render Prose and Tables commit fdc32f5

Fixed a real defect: attaching a structured table to a section used to replace its narrative text entirely, which is why calc tables had been restricted to only two sections. Prose now always renders first, with any resolvable table following it. Added audit-history front matter and four new table producers (proponent, applicability, GHG project-boundary, fixed monitoring parameters) driven by the plan's S-3 specification, taking the DOCX from 3 of 11 Verra table types wired to 8 of 11. 70 targeted tests passing, manually verified end-to-end on a Soc Son export.

PHASE-02 — Rebuild the Index on Real Section Spans commit d595e31

The core fix. Replaced whole-page indexing with true section-span chunking sourced from each document's pre-parsed text_blocks, keeping the old page-fragment path as a documented per-document fallback. Added methodology-family filtering (so a rice project stops citing waste-to-energy PDDs as provenance) and finally populated two index columns that had silently always been empty. Duplication fell from 73.4% to 2.7%; mean chunk length rose from 498 to 1,068 characters. One retrieval-diversity regression, caused by the new multi-chunk-per-document reality colliding with an old single-chunk-per-document query assumption, was caught and fixed directly in main before commit (see Findings).

Deferred — PHASE-04, 05, 06 not started

PHASE-04 (one real, $1-capped claude-code section draft), PHASE-05 (feeding the ACM0022 engine real waste-composition data and fixing a mass-conservation bug), and PHASE-06 (table-aware PDF ingestion behind an optional dependency) remain exactly as specified in the plan file, untouched. PHASE-04 was a spend-bounded smoke check rather than a hard code dependency for PHASE-05 — a future session pulling PHASE-05 forward should re-read its own Dependencies note before assuming it still needs PHASE-04 to have run first.

07 / Findings & Recommendation

Findings & Recommendation

The core retrieval defect is fixed for 13 of 17 documents. Duplication rate dropped from 73.4% to 2.7%, well inside the plan's ≤15% target; mean indexed chunk length rose from 498 to 1,068 characters, above the plan's 800-character target. A live check of section 4.4's example retrieval went from 2 distinct texts drawn from 1 document to 5 distinct texts across 5 documents.

An orchestrator-level fix beyond the phase's own diff. The PHASE-02 implementation surfaced, rather than silently patched over, a genuine tension in the plan's own specification: get_section_examples()'s query ranked results alphabetically by document name and took the first k — a design that assumed roughly one chunk per document per subsection, true before this phase, false after it. Once a document could legitimately contribute several chunks to one subsection, the alphabetically-first document(s) could exhaust the result budget before a second document was ever reached, which is exactly what was measured (2 distinct documents, below the plan's own ≥3 threshold). This was fixed directly on main: results are now ranked within each document by chunk position before slicing to k, so the top-k spans documents before it takes a second chunk from the same one. Re-measured afterward: 5 distinct documents.

An honest, unresolved gap: 4 of 17 documents still yield nothing, including the methodology text itself. These four .norm.json files were found to carry a single collapsed one-block body alongside an unrelated 50-entry heading list left over from an older extraction pass — the two never had real content to align in the first place. PHASE-02's own alignment check correctly detects this and falls back to the legacy page-fragment path, which also fails for the same underlying reason. The defect lives in ingest/normalize.py's heading detection for these specific PDFs, a layer explicitly out of scope for this phase (and one the plan's own risk register anticipated by name). No attempt was made to patch around it from inside the retrieval layer — the recommendation is to fix heading extraction at the source, not to loosen a downstream check to hide the gap.

The export defect is fixed cleanly. Structured tables no longer delete the prose they were meant to accompany; the DOCX now reflects what registered PDDs actually look like — narrative and table together — in 8 of 11 Verra table sections.

08 / Implementation Path

Implementation Path

Next: fix heading detection in normalize.py

The 4-document gap is now root-caused, not just observed. The next concrete step is a targeted, evidence-driven look at why _build_headings_and_blocks() finds zero real headings in these four specific PDFs while a separate, older extraction path still finds 50 — likely a PDF-structure edge case (image-based headings, unusual font encoding, or a layout this parser doesn't expect). This is squarely a normalize.py change, independent of anything in this push.

Then: resume PHASE-04 when ready to spend

With PHASE-02 and PHASE-03 both landed, the plan's --only-section smoke-test flag is unblocked. Running it (~$0.20 against a real Claude subscription, capped at $1) is the cheapest way to catch the class of output defect that only ever surfaces on real model output — as it did twice before in this project's history.

Then: PHASE-05, the calc mass-conservation fix

Independently valuable and not code-blocked by PHASE-04 (only originally sequenced after it). Fixes a real, previously measured bug: 33% of Soc Son's declared waste throughput is silently dropped before it reaches the emissions engine, and gives the engine the registered PDD's own published waste composition instead of guessing an even split.

Last: PHASE-06, table-aware ingestion

Lowest priority in the original plan and the only phase adding a new dependency (pdfplumber). Worth revisiting once the four-document gap above is closed, since better table extraction may also help recover heading structure in those same problem documents.

09 / Risks / Open Questions

Risks / Open Questions

Open questions

  • Is the normalize.py heading-detection failure specific to these 4 PDFs' structure, or a broader class the other 13 happened to avoid? Not yet investigated.
  • Now that retrieval draws from real, longer section text, has drafted-section quality on a real model materially changed? Untestable without running PHASE-04.
  • Does the S-3 GHG project-boundary table (authored from methodology knowledge, per the plan's ASM-005) actually match the ACM0022 source document's Section 5? It cannot be verified until the 4-document gap is closed and that document is retrievable — currently unverified.

Risks carried forward

  • Re-chunking changed the text injected into every drafting prompt. No committed artifact depends on it today (data/index/ is gitignored, the demo provider ignores retrieval content), but any future real-model run will see materially different grounding than past runs did.
  • The retrieval-diversity fix (ranking by chunk position per document) was made and verified by the orchestrating session, not by the phase agent that authored the surrounding diff — it is a small, isolated, well-tested change, but it sits slightly outside the original per-phase review boundary and is worth a second look.
  • PHASE-05's mass-conservation fix is expected to move Soc Son's crediting-period total in a currently unpredictable net direction (the plan's own risk register flags this explicitly) — deferring it here means that uncertainty is still fully open.
