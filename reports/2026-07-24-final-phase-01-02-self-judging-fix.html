01 / Executive Summary

Executive Summary

What was fixed

A drafting orchestrator component (SectionOrchestrator._run_judge_redraft_loop) used to default to letting a drafting provider judge its own output whenever no explicit override was set. That meant a real AI provider could evaluate its own work with no independent check — the exact defect that stopped a prior push from running the project's real-model proof at full scale. This pass extracted the project's already-correct "never self-judge" logic into a shared module and wired it into the one place that was still missing it.

What this unblocks

Running pdd-agent prove against the keyless claude-code provider — the project's long-standing milestone, attempted only once before in a deliberately small, bounded form — is now safe to run at full scale by default. That run itself (Phase 3) and a related corpus-capture task (Phase 4) were not executed in this pass; they remain open, deliberate follow-up actions.

Unplanned but material finding

Verifying the fix surfaced a real risk the plan flagged only in principle: on a machine with the AI CLI installed, the automated test suite itself would have started making real, live calls to that CLI during ordinary test runs — confirmed by direct reproduction, then closed with explicit test-side safeguards. See Section 6 and 7 for the full account; it is the most consequential finding of this pass.

Verified state

735 tests passing, 7 intentionally skipped, zero lint findings, full suite runtime back to its normal ~83-second baseline. Two commits on main: 4266be1 (Phase 1) and aae79b3 (Phase 2).

02 / Background & Objective

Background & Objective

PDD Agent drafts Verra carbon-credit project design documents using a corpus-grounded drafting pipeline with an automated review step: an AI "judge" scores each drafted section and can trigger up to several redraft attempts if it finds critical problems. Four consecutive prior development pushes on this repository built toward one milestone: proving the pipeline works with a real frontier AI model, not just the deterministic placeholder providers used for demos. The most recent of those pushes finally removed the last procurement blocker — a "keyless" provider that uses a locally installed AI command-line tool instead of requiring a paid API key — but its own closing report stopped short of actually running the full proof. The stated reason: the in-loop redraft judge still let a real provider judge its own work by default, an unbounded and unverified risk that made the team run only a small, deliberately bounded manual check instead.

The objective of this pass was narrow and specific: close that one gap (Phase 1–2 of a 4-phase plan), so that running the actual full-scale proof becomes a safe, deliberate action rather than a still-blocked one. Running that proof itself, and a separate, independent task to unlock live corpus data from a public registry, were scoped as later phases of the same plan and were intentionally left for a following pass.

05 / Methodology

Methodology

Each phase followed the same discipline: implement the change exactly as specified in the plan, then verify it empirically rather than by inspection alone — running the full automated test suite, the linter, and the formatter after every change, and only committing once all three were clean. Phase 2 in particular did not stop at "the tests pass" — a suspicious ~2x increase in full-suite runtime after the code change was treated as a finding to chase down, not noise to ignore, which is what surfaced the live-CLI risk documented in Section 6. That risk was confirmed with a direct, isolated reproduction (deliberately triggering the suspected behavior with instrumentation, in a sandboxed way that could not itself make a real external call) before being fixed, and the fix was re-verified the same way to confirm the risk was actually closed, not just no longer triggering the specific test that first exposed it.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Extract shared selection logic Done

The logic for "which provider should judge this drafting provider's output, and never let it judge itself" already existed correctly in one place in the codebase (the head-to-head provider scorecard used by the prove command) but was never reused anywhere else. This phase moved that logic into a new shared module (judge_selection.py) with a small addition — a convenience function for callers that need to resolve a judge for a single provider on the fly, rather than from a pre-computed list. The scorecard module was updated to import the shared logic instead of defining its own copy. Seventeen tests covering this logic were relocated into a dedicated test file; the scorecard's own test file shrank accordingly, with the total test count for this area unchanged — confirming the move preserved behavior exactly.

Phase 2 — Fix the in-loop redraft judge Done

The actual bug fix: the orchestrator's per-section redraft loop was rewired to call the new shared selection logic instead of a one-line default that silently picked the drafting provider as its own judge. The fix also caches that decision once per drafting run rather than recomputing it for every section (a run drafts dozens of sections), and it now correctly counts the judge's own token usage toward the run's cost — previously excluded. What made this phase take real effort was not the code change itself (about a dozen lines) but verifying it was actually safe — see the finding below.

Phase 3 — Run the real-model proof Not started

Now safe to run by default (that was the entire point of Phases 1–2), but involves real wall-clock time (tens of minutes) and subscription-billed AI usage. Treated as a deliberate follow-up action rather than something to trigger automatically at the end of a code-change pass.

Phase 4 — Live registry-API capture Not started

Independent of Phases 1–3 and not touched in this pass. Requires an interactive, devtools-based capture of a public registry's search API before it can be automated.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the primary bug is fixed and verified. The in-loop redraft judge no longer defaults to self-judging. A direct code check (grep for the old default expression) confirms the literal defect is gone, and three new regression tests assert the judge provider is never the drafting provider when an alternative is available, correctly falls back to a deterministic judge when nothing else is available, and is resolved only once per run rather than once per section.

Finding 2 — the most consequential discovery of this pass was not in the plan. After the Phase 2 code change, the full test suite still passed — but took roughly twice as long as normal (158 seconds versus an ~83-second baseline). Rather than treat "tests still pass" as sufficient, that timing anomaly was investigated directly. The cause: one test file registers a real instance of the AI-CLI-backed provider into a shared, process-wide registry and never removes it; combined with the AI CLI actually being installed on the machine running the tests, the newly-fixed judge-selection logic would correctly select that real provider as judge during later, unrelated tests — and then actually invoke the live CLI during what should have been a fully offline, mocked test run. This was proven, not assumed: a deliberate, sandboxed reproduction showed two real command invocations firing during a test run before the fix, and zero after. This also explains the timing anomaly — separately, each such judge-selection decision was independently probing a local network service with a multi-second timeout, adding real time even when it wasn't making a live CLI call. Both issues were fixed together by making the relevant tests explicitly force every real provider "unavailable" before exercising the judge path, and by caching the judge-selection decision once per run (Phase 2's original design intent, now correctly enforced by the same fix).

Recommendation. The code is ready for Phase 3. Because Phase 3 involves real cost and non-trivial run time, it should be scheduled as its own deliberate action — not appended automatically onto this one — with someone available to review the resulting scorecard artifacts once the run completes.

09 / Risks / Open Questions

Risks / Open Questions

Risks carried into Phase 3

  • A 36-section run against a real, live AI CLI has less predictable timing and failure modes than the deterministic placeholder providers this project has run almost exclusively until now.
  • Real, subscription-billed usage and meaningful wall-clock time mean Phase 3 should not be run casually or repeatedly without a reason.

Open questions

  • Whether the resulting drafted sections, once Phase 3 runs, will actually read as coherent, usable prose — this pass verified the pipeline is safe to run, not what the real output quality will be.
  • Whether the live public-registry API (Phase 4) will turn out to match the shape currently guessed in the codebase, or require a larger rework once actually captured.
